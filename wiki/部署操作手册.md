## 1. 部署前准备

### 1.1 确认 Docker 已安装

```bash
docker --version
# 预期输出：Docker version 24.x.x 或更高

docker compose version
# 预期输出：Docker Compose version v2.x.x
```

### 1.2 确认代码已克隆

```bash
cd ~/java-blog-system
ls -la
```

预期看到以下关键文件：

```
docker-compose.yml
blog-backend/
blog-admin/
blog-frontend/
```

### 1.3 检查 Docker 相关文件

```bash
# 确认 Dockerfile 存在
ls blog-backend/Dockerfile blog-admin/Dockerfile blog-frontend/Dockerfile

# 确认 nginx 配置存在
ls blog-admin/nginx.conf blog-frontend/nginx.conf

# 确认 docker 配置存在
ls blog-backend/src/main/resources/application-docker.yaml

# 确认数据库初始化脚本存在
ls blog-backend/sql/01-create_sql.sql
```

### 1.4 查看服务器 IP

```bash
ip addr show | grep 'inet ' | grep -v '127.0.0.1'
# 记下虚拟机 IP，后续访问需要用到
```

### 1.5 环境变量与 .env 配置（首次部署必读）

项目的敏感配置（数据库/Redis 密码、JWT 密钥、API 签名密钥等）统一通过环境变量注入：`docker-compose.yml` 与后端 `application-docker.yaml` 均使用 `${VAR:-默认值}` 占位。根目录提供 `.env.example` 模板，`.env` 已被 `.gitignore` 忽略，不会提交到 git。

**变量一览**（带 ★ 的项生产环境必须修改）：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| COMPOSE_PROFILES | — | Compose 服务分组（`search` = 附带 Elasticsearch 全文检索；`monitor` = 附带 Prometheus + Grafana 监控；可组合如 `search,monitor`） |
| MYSQL_ROOT_PASSWORD ★ | 123456 | MySQL root 密码（容器初始化、健康检查与维护用；后端应用使用专用账号连接，root 仅维护用） |
| MYSQL_DATABASE | dlbyy_z | 应用数据库名（仅首次建库时创建；已有数据卷的老部署请指回原库名 `dlbyy_zp_blog`） |
| MYSQL_USERNAME | blog_app | 后端连接 MySQL 的专用账号（仅首次建库时自动创建并授权；老部署请保持 `root`） |
| MYSQL_PASSWORD ★ | 123456 | `MYSQL_USERNAME` 账号的密码（mysql 侧与后端共用，两侧须一致；生产改为强密码） |
| MYSQL_PORT | 127.0.0.1:3306 | MySQL 宿主机端口映射，默认仅绑定本机回环（数据库不暴露公网）；需外部连接时改为 `3306` |
| REDIS_PASSWORD ★ | 123456 | Redis 密码 |
| JWT_SECRET ★ | 内置开发默认值 | JWT 签名密钥（≥64 字符，强随机） |
| API_SIGNING_SECRET ★ | 内置开发默认值 | API 请求签名密钥（须与前端构建密钥一致） |
| CORS_ALLOWED_ORIGINS ★ | `*` | CORS 来源白名单（逗号分隔，对应后端 `security.cors.allowed-origins`）；`*` 仅开发用，生产填精确域名如 `https://yourdomain.com,https://admin.yourdomain.com` |
| SWAGGER_ENABLED | false | 接口文档开关（Docker 默认 false，本地开发默认 true）；关闭时 `/api/doc.html` 等不可访问，联调排查时可临时开启 |
| BLOG_SEARCH_ENABLED | false（模板预设 true） | 是否启用 Elasticsearch 全文检索（true 需 COMPOSE_PROFILES 包含 search） |
| GRAFANA_ADMIN_USER ★ | admin | Grafana 管理员用户名（启用 monitor 分组时生效） |
| GRAFANA_ADMIN_PASSWORD ★ | admin123 | Grafana 管理员登录密码（启用 monitor 分组时生效，生产必改） |
| OSS_ENDPOINT | 占位符 | OSS 对象存储 Endpoint（启用 oss 存储时配置） |
| OSS_ACCESS_KEY_ID | 占位符 | OSS AccessKey ID |
| OSS_ACCESS_KEY_SECRET | 占位符 | OSS AccessKey Secret |
| OSS_BUCKET_NAME | 占位符 | OSS Bucket 名称 |
| OSS_URL_PREFIX | 占位符 | OSS 文件访问 URL 前缀 |

**操作步骤**：

1. 在项目根目录复制模板并编辑：

```bash
cp .env.example .env
vim .env   # 按需修改，重点核对带 ★ 的项
```

2. 启动服务（`.env` 中的变量会自动注入 docker-compose.yml 与后端容器）：

```bash
docker compose up -d --build
```

**重要说明**：

- **JWT_SECRET**：长度必须 ≥ 64 字符（HS512 要求），生产环境务必替换为强随机值，可用 `openssl rand -base64 64` 生成。
- **API_SIGNING_SECRET**：须与前端构建时的签名密钥一致，否则签名校验失败、管理后台无法登录：
  - blog-admin：构建时环境变量 `VITE_API_SIGNING_SECRET`，或 `blog-admin/.env.production` 中的取值
  - blog-app：发行前修改 `blog-app/common/env.js` 中的 `SIGNING_SECRET`
- **专用账号仅首次建库生效**：`MYSQL_DATABASE`/`MYSQL_USERNAME`/`MYSQL_PASSWORD` 只在 MySQL 数据卷**首次初始化（数据目录为空）**时由 mysql 镜像自动创建库与账号。已有数据卷的老部署升级时，须在 `.env` 中把这三项指回原值（`dlbyy_zp_blog`/`root`/原密码），否则后端会因账号或库不存在而连不上数据库。
- **改密不回溯**：`MYSQL_ROOT_PASSWORD` 仅在 MySQL 数据卷**首次初始化**时生效。若数据卷已用旧密码初始化，事后修改 `.env` 中的密码不会同步进数据库（后端会因密码不符而连接失败），需二选一处理：
  - 进容器手动改密（保留数据）：

    ```bash
    docker exec blog-mysql mysql -uroot -p<旧密码> -e "ALTER USER 'root'@'%' IDENTIFIED BY '<新密码>'; FLUSH PRIVILEGES;"
    ```

  - 删除数据卷重建（⚠️ 清空全部数据）：`docker compose down -v` 后再重新启动

## 2. Docker 镜像加速器配置

国内网络环境拉取 Docker Hub 镜像可能超时或被限流（429 Too Many Requests），**必须配置镜像加速器**。

### 2.1 查看当前配置

```bash
cat /etc/docker/daemon.json
```

### 2.2 配置镜像加速器

```bash
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://dockerpull.org",
    "https://docker.xuanyuan.me"
  ],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  }
}
EOF
```

### 2.3 重启 Docker 生效

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

### 2.4 验证镜像加速

```bash
docker info | grep -A 5 "Registry Mirrors"
```

### 2.5 （推荐）配置阿里云专属加速器

公共镜像加速器可能被限流，阿里云提供免费的个人专属加速器，稳定性最好：

1. 访问 https://cr.console.aliyun.com/cn-hangzhou/instances/mirrors
2. 使用阿里云账号登录
3. 页面会显示你的专属加速器地址，格式类似：`https://xxxxxx.mirror.aliyuncs.com`
4. 替换 daemon.json：

```bash
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": [
    "https://xxxxxx.mirror.aliyuncs.com",
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run"
  ],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  }
}
EOF

sudo systemctl daemon-reload
sudo systemctl restart docker
```

> 将 `xxxxxx` 替换为你的阿里云加速器 ID。

## 3. 基础镜像预拉取

在执行 `docker compose up` 之前，建议先单独拉取所有基础镜像。这样可以避免构建时因镜像拉取超时而失败，也便于排查网络问题。

### 3.1 需要拉取的镜像列表

按服务依赖顺序排列：

| 序号 | 镜像名称 | 用途 | 大小参考 | 拉取命令 |
|------|----------|------|----------|----------|
| 1 | `mysql:8.0` | 数据库 | ~600MB | `docker pull mysql:8.0` |
| 2 | `redis:7-alpine` | 缓存 | ~40MB | `docker pull redis:7-alpine` |
| 3 | `eclipse-temurin:17-jdk-jammy` | 后端构建阶段 | ~350MB | `docker pull eclipse-temurin:17-jdk-jammy` |
| 4 | `eclipse-temurin:17-jre-jammy` | 后端运行阶段 | ~250MB | `docker pull eclipse-temurin:17-jre-jammy` |
| 5 | `node:18-alpine` | 前端构建阶段 | ~150MB | `docker pull node:18-alpine` |
| 6 | `nginx:1.25-alpine` | 前端运行阶段 | ~50MB | `nginx:1.25-alpine` |

> **说明**：`eclipse-temurin:17-jdk-jammy` 与 `eclipse-temurin:17-jre-jammy` 共享 Ubuntu jammy 基础层，拉取第一个后第二个会快很多。

### 3.2 逐个拉取镜像

```bash
# 1. 拉取 MySQL（最先需要）
docker pull mysql:8.0

# 2. 拉取 Redis
docker pull redis:7-alpine

# 3. 拉取后端构建镜像（JDK，较大）
docker pull eclipse-temurin:17-jdk-jammy

# 4. 拉取后端运行镜像（JRE，与 JDK 共享层，很快）
docker pull eclipse-temurin:17-jre-jammy

# 5. 拉取前端构建镜像
docker pull node:18-alpine

# 6. 拉取前端运行镜像
docker pull nginx:1.25-alpine
```

### 3.3 验证镜像已拉取

```bash
docker images | grep -E 'mysql|redis|eclipse-temurin|node|nginx'
```

预期输出包含以上 6 个镜像。

### 3.4 如果拉取超时或 429

```bash
# 查看拉取错误信息
docker pull mysql:8.0 2>&1 | tail -5

# 解决方案：
# 1. 确认镜像加速器已配置（见第 2 节）
# 2. 使用阿里云专属加速器（见第 2.5 节）
# 3. 重试拉取
docker pull mysql:8.0
```

## 4. 一键启动全部服务

### 4.1 执行启动命令

```bash
cd ~/java-blog-system
docker compose up -d --build
```

- `-d`：后台运行
- `--build`：构建镜像（首次必须加）

### 4.2 启动顺序说明

Docker Compose 按依赖顺序启动服务：

```
MySQL（启动 + 健康检查通过）
    ↓
Redis（启动 + 健康检查通过）
    ↓
blog-backend（Maven 编译 → JAR 打包 → 启动 → 健康检查通过）
    ↓
blog-admin（npm 编译 → nginx 启动）
blog-frontend（npm 编译 → nginx 启动）
```

### 4.3 启动进度查看

```bash
# 查看全部服务实时日志
docker compose logs -f

# 单独查看后端构建与启动日志（最耗时的部分）
docker compose logs -f blog-backend

# 当后端日志出现以下字样时，说明后端已启动成功：
# "Started JavaBlogApplication in x.xxx seconds"
```

### 4.4 首次构建耗时参考

| 阶段 | 预计耗时 | 说明 |
|------|----------|------|
| MySQL + Redis 启动 | 30-60s | 基础服务就绪 |
| 后端 Maven 依赖下载 | 3-10min | 首次需下载所有依赖（走阿里云 Maven 镜像） |
| 后端编译打包 | 1-2min | Maven 编译 + JAR 打包 |
| 后端启动 | 30-60s | Spring Boot 启动 |
| 管理后台 npm install + build | 2-5min | 首次需下载 npm 依赖 |
| 前台门户 npm install + build | 2-5min | 首次需下载 npm 依赖 |
| **总计** | **8-20min** | 取决于网络与服务器性能 |

> 后续重新构建会利用 Docker 缓存层，耗时大幅减少。

## 5. 逐服务状态检查

### 5.1 查看全部服务状态

```bash
docker compose ps
```

预期输出（全部为 `running` 或 `healthy`）：

```
NAME              IMAGE                              STATUS                    PORTS
blog-admin        blog-admin                         Up X minutes              0.0.0.0:8081->80/tcp
blog-frontend     blog-frontend                      Up X minutes              0.0.0.0:8082->80/tcp
blog-backend      blog-backend                       Up X minutes (healthy)    0.0.0.0:8080->8080/tcp
blog-mysql        mysql:8.0                          Up X minutes (healthy)    0.0.0.0:3306->3306/tcp
blog-redis        redis:7-alpine                     Up X minutes (healthy)    0.0.0.0:6379->6379/tcp
```

### 5.2 健康检查说明

| 服务 | 健康检查方式 | start_period |
|------|-------------|--------------|
| MySQL | `mysqladmin ping` | 30s |
| Redis | `redis-cli ping` | 10s |
| blog-backend | `curl http://localhost:8080/api/portal/stats` | 60s |

> `blog-backend` 的健康检查 `start_period` 为 60 秒，在此期间即使检查失败也不会标记为 unhealthy。

### 5.3 查看各服务日志

```bash
# 查看后端日志（排查启动失败）
docker compose logs -f blog-backend

# 查看 MySQL 日志
docker compose logs -f mysql

# 查看 Redis 日志
docker compose logs -f redis

# 查看管理后台日志
docker compose logs -f blog-admin

# 查看前台门户日志
docker compose logs -f blog-frontend
```

### 5.4 检查容器资源占用

```bash
docker stats --no-stream
```

## 7. 常见部署问题排查

### 7.1 镜像拉取 429 Too Many Requests

**现象**：

```
failed to resolve source metadata for docker.io/library/xxx: unexpected status from GET request: 429 Too Many Requests
```

**原因**：公共镜像加速器被限流。

**解决**：

```bash
# 1. 配置阿里云专属加速器（见第 2.5 节）
# 2. 重启 Docker
sudo systemctl restart docker
# 3. 重试拉取
docker pull <镜像名>
```

### 7.2 后端构建 apt-get 超时

**现象**：`docker compose up --build` 卡在 `RUN apt-get update` 超过 5 分钟。

**原因**：容器内 `apt-get` 从 `archive.ubuntu.com` 下载缓慢。

**解决**：当前 Dockerfile 已移除 `apt-get`，使用 Docker `ADD` 指令直接下载 Maven。如仍遇到此问题，确认使用的是最新 Dockerfile：

```bash
# 检查 Dockerfile 是否包含 ADD 指令（而非 apt-get）
grep "ADD" blog-backend/Dockerfile
```

### 7.3 Maven 下载慢 / 构建卡住

**现象**：后端构建卡在 `mvn dependency:go-offline` 或 `mvn package` 超过 10 分钟。

**原因**：Maven 从中央仓库下载依赖缓慢。

**解决**：当前 Dockerfile 已配置阿里云 Maven 镜像。确认配置存在：

```bash
grep "aliyun" blog-backend/Dockerfile
# 预期看到阿里云 Maven 镜像 URL
```

如仍慢，可手动在宿主机预编译 JAR 后修改 Dockerfile 直接复制：

```bash
# 在宿主机（需有 JDK + Maven）
cd blog-backend
mvn clean package -DskipTests
# 然后修改 Dockerfile 跳过编译阶段，直接 COPY target/*.jar
```

### 7.4 端口冲突

**现象**：容器启动报错 `bind: address already in use`。

**解决**：

```bash
# 查看占用端口的进程
sudo lsof -i :8080
sudo lsof -i :8081
sudo lsof -i :8082

# 停止占用进程
sudo kill -9 <PID>

# 或修改 docker-compose.yml 中的端口映射
# 例如将 "8080:8080" 改为 "9090:8080"
```

### 7.5 数据库连接失败

**现象**：后端日志报错 `Communications link failure` 或 `Access denied for user 'root'`。

**解决**：

```bash
# 1. 确认 MySQL 容器已健康启动
docker compose ps mysql
# 状态应为 healthy

# 2. 检查后端配置中的数据库连接信息
cat blog-backend/src/main/resources/application-docker.yaml | grep -A 5 datasource
# host 应为 mysql，password 应为 123456

# 3. 手动测试数据库连接
docker exec blog-mysql mysql -uroot -p123456 -e "SHOW DATABASES;"
# 应看到 dlbyy_zp_blog 数据库

# 4. 如数据库未初始化，手动执行 SQL
docker exec -i blog-mysql mysql -uroot -p123456 dlbyy_zp_blog < blog-backend/sql/01-create_sql.sql
```

### 7.6 前端页面空白 / 404

**现象**：访问管理后台或前台门户显示空白页或 404。

**解决**：

```bash
# 1. 确认后端健康检查通过（前端依赖后端）
docker compose ps blog-backend
# 状态应为 healthy

# 2. 管理后台必须访问 /admin/ 路径（含尾部斜杠）
# 正确：http://<IP>:8081/admin/
# 错误：http://<IP>:8081/

# 3. 前台门户必须访问 /blog/ 路径（含子路径）
# 正确：http://<IP>:8082/blog/
# 错误：http://<IP>:8082/
```

## 9. 上线前安全检查

对公网开放访问（正式上线）前，逐项核对以下清单，全部通过后再对外提供服务。所有检查项均针对项目根目录的 `.env` 文件，修改后需 `docker compose up -d` 重启生效。

### 9.1 检查清单

| # | 检查项 | 要求 | 不满足的风险 |
|---|--------|------|--------------|
| 1 | 带 ★ 的 `.env` 项已改为强随机值 | `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` / `REDIS_PASSWORD` / `JWT_SECRET` / `API_SIGNING_SECRET` / `GRAFANA_ADMIN_PASSWORD` 全部替换，不得保留默认值（如 123456、admin123、内置开发密钥） | 密码被猜解、JWT 可被伪造、监控面板被登录 |
| 2 | `CORS_ALLOWED_ORIGINS` 已改为精确域名 | 填写实际域名（逗号分隔），如 `https://yourdomain.com,https://admin.yourdomain.com`；**勿保留 `*`**（默认 `*` 仅开发用） | 任意来源站点可携带凭证调用接口 |
| 3 | MySQL 使用专用账号 + 强密码 | 后端以 `blog_app`（`MYSQL_USERNAME`）连接并使用强密码（`MYSQL_PASSWORD`）；`root` 仅维护用 | 后端被攻破后攻击者直接拿到 root 权限 |
| 4 | `SWAGGER_ENABLED=false` | 接口文档不对外暴露；`/api/doc.html` 等应不可访问（Docker 默认即 false，确认未被改回） | 接口结构对外泄露，扩大攻击面 |
| 5 | `MYSQL_PORT` 保持 `127.0.0.1:3306` | 数据库仅绑定本机回环，不暴露公网；确需外部连接时才改为 `3306` | 数据库端口被公网扫描与爆破 |

### 9.2 快速验证命令

```bash
# 检查 2：确认 CORS 白名单不含 *
grep CORS_ALLOWED_ORIGINS .env

# 检查 4：确认 Swagger 已关闭（预期 404 或 403，非文档页面）
curl -I http://localhost:8080/api/doc.html

# 检查 5：确认 MySQL 仅监听本机回环（预期 127.0.0.1:3306，而非 0.0.0.0:3306）
docker compose ps mysql --format '{{.Name}} {{.Publishers}}'

# 检查 3：确认后端以专用账号连接（默认 blog_app，密码以 .env 为准）
docker exec blog-mysql mysql -uroot -p'<root密码>' -e "SELECT user, host FROM mysql.user;"
```

### 9.3 老库升级提示（已有数据卷时必读）

`MYSQL_DATABASE` / `MYSQL_USERNAME` / `MYSQL_PASSWORD` **仅在数据卷首次初始化（数据目录为空）时生效**。若是从旧版本升级、`blog_mysql_data` 数据卷已存在：

- 必须在 `.env` 中把这三项**指回原值**：`MYSQL_DATABASE=dlbyy_zp_blog`、`MYSQL_USERNAME=root`、`MYSQL_PASSWORD=<原密码>`；
- 否则后端会按新默认值连接 `dlbyy_z` 库与 `blog_app` 账号，而旧数据卷中并不存在它们，导致后端连不上数据库（报 `Access denied` 或 `Unknown database`）；
- 如需迁移到专用账号，可进容器手动创建库/账号并授权后再切换 `.env`（保留数据，参考 1.5 节「改密不回溯」的处理方式）。
